# C → LLVM IR 다음 학습 개선 제안서

작성일: **2026-11-16** · 상태: **검토용 제안** · 신규 데이터 생성·GPU 학습은 아직 시작하지 않음

## 1. 제안 요약

**Qwen3-4B를 유지하고, 고정 타깃 속성 분리 → 상수·연산·복합 구조 데이터 보강 → 동일 추론 조건의 실행 평가 순서로 개선한다.** 첫 실험은 기존 880개 학습 함수를 그대로 사용해 출력 프로필 변경의 효과를 확인한다. 그 뒤 새 2,000쌍을 추가하는 단계로 진행한다. 모델 크기, 학습량, 데이터, 출력 형식을 한 번에 바꾸지 않는다.

가장 큰 개선 대상은 문법이 아니라 **계산 의미의 보존**이다. 현재 동결 시험은 LLVM 검증·컴파일 108/110(98.2%)에 비해 실행 일치가 72/110(65.5%)이고, combined는 8/22(36.4%)다. `+sha` 같은 타깃 속성 오류는 별도의 출력 형식 문제로 관리한다.

| 우선순위 | 제안 | 완료 판단 |
|---|---|---|
| P0 | 원본 시험·모델·평가 정책 동결, greedy 기준 재확인 | 이후 실험과 비교 가능한 기준 실행 확보 |
| P1 | 고정 `target-cpu`·`target-features`를 생성 목표에서 분리 | 정답 변환·복원 전량 검증, 타깃 속성 오생성 차단 |
| P1 | uint32 상수·연산 및 복합 표현식·제어 흐름 보강 | 고정 개발 패널의 함수 실행 일치율 개선 |
| P1 | 기존 구조 해시 유지 + 더 거친 family 단위의 미노출 평가 | IID와 family OOD 점수를 분리 보고 |
| P2 | 실행 일치율 기반 checkpoint 선택, 데이터 노출량 비교 | 동일 조건의 개발 결과로만 후보 선택 |
| P3 | 국소 SMT 검증, 더 큰 모델, 추가 문법 | 선행 단계 결과와 자원 근거가 있을 때 별도 실험 |

이 문서의 새 데이터 수량·목표치·시간 상한은 **제안값**이다. 검증이 끝난 성능이나 확보된 GPU 할당량이 아니다.

## 2. 첨부 보고서 검토와 사실 보완

첨부 보고서의 문법/의미 차이, 실패를 분모에서 제외하지 않는 평가, combined 보강, 상수 및 연산 보존, 새로운 최종 시험 세트 제안에 동의한다. 다만 다음 사항을 보완해야 한다.

| 첨부 보고서의 설명 또는 의문 | 프로젝트 기록으로 확인한 내용 | 다음 실험에 반영 |
|---|---|---|
| 학습 방식·epoch·학습률이 불명확 | NF4 double-quant QLoRA, FP16 계산, rank 8 / alpha 16 / dropout 0.05, all-linear, LR 1e-4, 배치 1×누적 4, 220 step / 1 epoch | 기존 설정을 초기 통제 조건으로 유지 |
| 데이터 분할 비율이 불명확 | 학습 880 / 검증 110 / 시험 110, 80:10:10 | 기존 분할과 역사적 결과 보존 |
| 구조 단위 분리가 필요 | 이미 `structure_id`로 상수·변수명 변형을 묶고 연산자·문장 구조를 보존해 분리함. 구조·C·IR의 분할 간 동일 해시가 없음 | 더 거친 family 평가를 추가하되, 기존 분할을 단순 무작위 분할로 묘사하지 않음 |
| 예시 `uint32_t f(uint32_t x)` | 실제 학습 서명은 `unsigned int compute(unsigned int x, unsigned int y)` | 2인자 uint32 함수 범위를 유지 |
| for/while 예시 | 현재 생성기는 정해진 for 형태, 최대 16회, 중첩 반복 없음 | while·중첩 반복·포인터는 이번 기본 범위에서 제외 |
| loss 0.004449의 해석 | teacher-forced 검증 loss이며 함수 단위 실행 성공률과 다른 지표 | checkpoint 선택의 단독 기준으로 쓰지 않음 |
| 속도 약 3시간 20분 | T4 두 worker가 55함수씩 처리한 전체 경과 시간. 함수당 평균 212.1초, worker 생성 시간 합계 약 6.48시간 | 경과 시간, GPU 작업량, 플랫폼 과금/할당량을 구분 |

기존 validation 20함수의 70%는 sampling과 300초 제한으로 측정됐다. 후속 시험 65.5%는 greedy·600초·4,096토큰 조건이다. 둘을 직접 비교해 성능 상승/하락을 주장하지 않는다.

Kaggle 시험은 NF4 기반 모델+adapter이고, 로컬 Ollama는 F16 병합/MLX 경로다. 동일한 모델 계보라도 수치 계산·렌더링 경로가 달라 재평가가 필요하다. 로컬 `+sha` 사례로 Kaggle의 65.5%를 다시 계산하지 않는다.

## 3. 데이터 생성기와 현재 분할의 범위

### 3.1 지금의 1,100쌍이 만들어진 방식

기본 100쌍과 확장 1,000쌍을 합쳤다. 각 분류는 220쌍이다. 생성기는 외부 모델이 임의 작성한 C를 수집하는 대신, 시드가 고정된 AST를 만들고 C로 렌더링한다. 연산은 uint32 모듈러 산술·비트 연산이고 시프트는 상수 0~31이다. 분기는 주로 XOR와 단일 비트 마스크 검사이며, 반복 횟수는 `(x & 15u) + (y & 1u)`다. combined는 반복문 안 분기와 반복문 이후 분기를 결합한다.

각 후보는 Python AST 해석기, C O0 실행, 저장 IR 실행, C UBSan 실행으로 확인한다. 입력은 경계값 전체 조합 64개와 고정 난수 192개이며, 제어 흐름 증인 탐색을 지원한다. 현재 코퍼스는 함수당 256개로 구성돼 있다. 이 절차는 유한 검사이며 모든 입력에서의 동등성 증명은 아니다.

기존 `structure_id`는 상수 값과 변수 구분·이름을 지우고, 연산자와 표현식/문장 구조를 남긴 해시다. 단순히 변수명과 숫자만 바꿔 학습/시험에 배치한 분할은 아니다. 다만 공통 생성 문법과 상위 템플릿을 공유하므로 일반 C에 대한 일반화까지 입증하지는 않는다.

### 3.2 이번에 추가로 점검한 결과

읽기 전용 점검 결과는 [evidence.json](../../training/proposals/v002/evidence.json)에 있다.

- 코퍼스 파일 무결성과 880/110/110 분할 검사 통과.
- 정답 1,100개의 `target-features` 목록은 전부 동일하다.
- 정확한 `+sha` 항목은 0개, `+sha2`와 `+sha3`는 각각 1,100개다. 따라서 로컬 `+sha`는 정답에 포함된 잘못된 라벨을 그대로 외운 사례로 보이지 않는다.
- `target-cpu`와 `target-features` 문자열은 전체 정답 IR **문자 수의 약 9.82%**다. 이는 토큰 감소율이나 속도 개선율이 아니다. 실제 토큰·지연시간은 실험으로 측정해야 한다.

| 분류 | 시험 함수 중 더 거친 모양을 학습과 공유 |
|---|---:|
| arithmetic | 4/22 |
| bitwise | 4/22 |
| branch | 1/22 |
| loop | 5/22 |
| combined | 0/22 |

이 사후 탐색 키는 새로운 진단 기준이며, 기존 분할 누출이나 암기를 입증한 것은 아니다. 특히 combined는 이 기준의 공유가 없어도 성능이 낮다. 따라서 오류 전체를 데이터 중복 탓으로 설명할 수 없다.

## 4. 개선 우선순위

### 4.1 고정 타깃 속성을 모델의 생성 책임에서 분리

새 프로필에서는 우선 `target-cpu`·`target-features` 두 항목만 대상으로 한다. 모델은 해당 두 항목을 제외한 유효 LLVM 모듈을 생성하고, 버전이 고정된 프로필 조립기가 필요한 값을 붙인다. `target triple`, datalayout, 함수 본문, 타입, 정렬, `noundef`, `nuw`/`nsw`, 기타 의미·ABI에 관련된 속성을 무작정 삭제하지 않는다.

필수 조건은 다음과 같다.

1. 기존 원본 IR·manifest·시험 보고서는 수정하지 않는다. 별도 `profile_id`와 변환기 버전을 사용한다.
2. 정답 변환 → 프로필 복원 경로를 1,100개 전량에 대해 LLVM 검증 및 기존 입력 실행으로 확인한다. 함수 명령·리터럴·피연산자는 변하지 않아야 한다.
3. 새 학습 모델이 생성 금지된 CPU 속성을 다시 출력하면 프로필 계약 위반으로 기록한다. 조립기가 임의로 계산 오류나 SSA 오류를 고치지 않는다.
4. `raw-generated.ll`, `assembled.ll`, 변환 diff와 각각의 해시를 보존한다. 조립된 모듈의 성공을 원문 모델의 성공으로 바꿔 보고하지 않는다.
5. v1 원문 엄격 점수, 공통 프로필을 적용한 시스템 점수, LocalTestPipeline의 `+sha` 경고 허용 점수는 서로 다른 열로 보고한다.

로컬의 `--not-allow-sha`는 엄격 평가에 사용하고, 기본 경고 허용은 실험 편의를 위한 제품 동작으로 유지한다. 경고를 허용했다고 데이터나 모델이 고쳐진 것은 아니다.

### 4.2 상수는 문자열 복사보다 uint32 값과 연산을 보존

실행 오답 36개 중 16개는 명령 구조가 같고 숫자 리터럴만 달랐다. 이는 휴리스틱 분류이며, 원인을 숫자 기억 실패 하나로 단정할 수 없다. C 상수식의 계산, 부호 표현 변환, 오버플로, 연산자 누락 등이 함께 작용할 수 있다.

학습 예제는 0·1·31·32 경계와 `2^k±1`, `0xffffffffu`, 큰 난수 상수, 마스크, 0/31 시프트, 중간 오버플로, 상수식 접기 사례를 포함한다. **시프트 피연산자 값 32는 허용하지 않고**, 32라는 값이 결과/일반 상수로 등장하는 경우와 시프트 횟수 0~31을 구분한다.

C의 `4294967295u`와 IR의 `i32 -1`은 같은 비트 패턴일 수 있다. 텍스트 일치만 강제하지 않고 uint32 값과 실제 실행으로 판단한다. 초기에 숫자 전용 토큰이나 loss 가중치를 변경하지 말고, 검증된 데이터 보강의 효과부터 확인한다.

### 4.3 표현식과 복합 제어 흐름의 데이터 흐름 보존

나머지 실행 오답 20개에는 연산 교체·명령 누락·피연산자 변경이 있다. combined 14오답은 모두 LLVM 검증과 컴파일을 통과했다.

새 예제는 누적값의 읽기/갱신 순서, 비가환 연산의 피연산자 순서, 괄호/우선순위, 반복 내부 분기, 분기 후 값 사용, 반복 전후 분기의 조합을 단계적으로 늘린다. 단순히 기존 실패 함수의 숫자만 바꿔 복제하지 않는다. 새 템플릿을 도입하면 AST 검증·렌더러·Python 의미 해석·커버리지 생성까지 함께 검증한다.

반복은 우선 최대 16회, 단일 반복을 유지한다. 중첩 반복, while, 포인터, 배열, 함수 호출, signed 연산은 별도 문법 버전의 과제로 남긴다.

## 5. 다음 데이터셋 설계

### 5.1 규모: 기존 학습 880 + 신규 2,000 = 총 2,880쌍

| 구분 | 개수 | 용도 |
|---|---:|---|
| 기존 학습 재사용 | 880 | 기존 범위 성능 유지와 비교 |
| 신규 학습 | 1,600 | 상수·연산 및 구조 다양성 보강 |
| 신규 개발 검증 | 200 | checkpoint/실험 선택; IID 150 + family OOD 50 |
| 신규 최종 시험 | 200 | 동결 후보의 마지막 비교; IID 100 + family OOD 100 |
| 합계 | **2,880** | 학습 2,480 / 신규 검증 200 / 신규 시험 200 |

기존 validation 110개는 별도 회귀 진단용으로 보존한다. 이미 분석에 사용한 기존 test 110개는 역사적/진단용으로만 보존하고 새 최종 점수로 재사용하지 않는다. 둘 다 위 학습 2,480개에 넣지 않는다.

신규 학습 1,600개 구성은 아래를 시작 제안으로 한다. combined 비중을 높이되 다른 분류의 회귀를 관찰한다.

| 분류 | 신규 학습 | 기존 176개 포함 후 |
|---|---:|---:|
| arithmetic | 240 | 416 |
| bitwise | 320 | 496 |
| branch | 160 | 336 |
| loop | 240 | 416 |
| combined | 640 | 816 |
| 합계 | **1,600** | **2,480** |

신규 검증·시험은 각각 분류별 40개로 균형을 맞춘다. 목표 수량은 후보 거절률과 family 수를 확인한 뒤 조정할 수 있으나, 조정은 시험 생성·열람 전에 문서와 manifest에 기록한다. 수량 충족을 위해 중복·검증 조건을 완화하지 않는다.

실제 로컬 입력과의 차이도 줄인다. 매우 짧은 `return x + y;` 같은 기본 함수와 기본 연산별 단위 예제를 신규 학습 내부에 포함한다. `_Static_assert` 유무·공백·변수명 같은 입력 표현 변형은 같은 AST 그룹 안에서만 관리한다. 변형을 독립적인 새 구조 수량으로 세지 않으며, 이를 도입할 경우 B1에는 적용하지 않고 B2 데이터 보강 패키지의 일부로 명시한다. 학습/검증/시험 사이에 같은 함수의 표현 변형이 넘어가면 안 된다.

### 5.2 분할과 노출 방지

- source·IR·기존 structure 해시 검사는 계속 유지하고 원본 1,100쌍과도 중복을 검사한다.
- family 정의는 후보 생성 전에 고정한다. 출발점은 연산자·숫자·식별자를 지운 AST 문장/표현식 모양이며, 제어 흐름 템플릿 ID와 난이도 태그도 저장한다. family는 보편적인 의미 동등성 분류가 아니라 이 실험의 일반화 기준이다.
- IID는 학습과 같은 상위 문법 계열에서 뽑되 기존 structure는 겹치지 않는다. family OOD는 해당 family가 전체 기존 코퍼스 및 새 학습에 없도록 한다.
- OOD 개발 family와 최종 시험 family도 서로 분리한다. 최종 IID와 OOD의 정의·추출 순서·분포를 미리 기록한다.
- 50개 고정 개발 패널은 기존 validation 25개와 신규 validation 25개, 분류별 총 10개로 구성한다. 신규 25개는 IID 15/OOD 10으로 배분한다. 초기 프로필 단독 실험에는 기존 25개 부분을 사용하고, 신규 데이터 완성 뒤 모든 후보의 누락된 개발 부분을 같은 설정으로 채운다.
- 시험 코퍼스를 만든 뒤 학습 작업에는 시험 C·IR·기대 실행값을 넣지 않는다. 최종 추론 작업에는 시험 프롬프트만 공급한다. 200개 최종 시험은 모델·checkpoint·후처리·제한을 동결한 후에만 실행한다.
- 개발 반례로 새 데이터를 채굴할 때 변형 전체를 같은 학습 family에 둔다. 최종 시험의 개별 오류를 보고 그 변형을 학습에 넣은 뒤 같은 시험을 다시 최종 점수로 발표하지 않는다.

### 5.3 검증과 입력 강화

신규 정답은 기존의 Python oracle / C O0 / IR 실행 / C UBSan 일치를 유지한다. 추가 입력은 함수의 상수·마스크·분기 임계값을 기반으로, 경계/오버플로와 반복 0·1·15·16을 확인하도록 설계한다. 특정 경로를 방문할 수 없는 후보는 사유를 기록한다. AST 추적 커버리지와 네이티브 바이너리 계측을 혼동하지 않는다.

개발 생성 평가는 256입력으로 빠르게 실행하고, 최종 시험은 **함수당 1,024입력 이상**을 목표로 한다. 기본 256개, 상수/제어 증인, 별도 난수로 채우며 생성 전에 정책을 고정한다. 성공 기준은 선택된 모든 입력의 일치다. 입력 증가로 최종 점수가 더 낮아질 수 있으므로 v1의 256입력 점수와 단순 비교하지 않는다. 256입력 기준의 보조 열도 함께 보존한다.

길이·AST 노드 수·표현식 깊이·분기 수·의존 사슬·리터럴 개수·출력 토큰 수를 저장하고, 각 분할 분포를 공개한다. 학습 context 4,096을 시작 범위로 검토하되 최대 길이의 전체 학습 step을 먼저 시험한다. 초과 후보는 미리 정한 범위 규칙으로 거절하며 IR을 잘라 학습하지 않는다.

## 6. 학습 및 비교 실험

모든 새 adapter는 **같은 Qwen3 기반 리비전에서 새로 시작**한다. 단계별로 adapter를 계속 이어 학습하면 이전 데이터 노출이 섞여 효과를 분리하기 어려우므로, 이번 기본 비교에서는 사용하지 않는다.

| 실험 | 학습 데이터·출력 | 최초 학습량 | 확인하려는 효과 |
|---|---|---:|---|
| B0 | 보존한 기존 adapter, v1 원문 | 추가 학습 없음 | greedy로 재측정한 기준 모델 |
| B1 | 기존 880개, 고정 CPU 속성 분리 프로필 | 220 step / 1 epoch | 출력 프로필만 바꾼 효과 |
| B2 | 기존 880 + 신규 학습 1,600, 동일 새 프로필 | 620 step / 1 epoch | 전체 데이터 보강 패키지 효과 |
| 선택적 B2a/B2b | 기존 880 + 동일 크기의 보강 묶음 800씩 | 각각 420 step | 상수 중심/구조 중심 보강의 기여 탐색 |
| 선택적 B3 | B2와 같은 데이터·프로필 | 별도 계획 | LR 또는 데이터 노출량 하나만 변경 |

B2에서 데이터 양과 구성 비중이 함께 바뀌므로 결과만으로 상수 보강과 combined 보강 각각의 효과를 확정하지 않는다. 기여를 분리할 필요가 생기면 같은 수량·분류·길이 구간을 맞춘 B2a/B2b를 추가한다. 이 선택 실험은 첫 필수 실행 묶음에 포함하지 않는다.

초기 설정은 rank 8, alpha 16, dropout 0.05, all-linear, LR 1e-4, microbatch 1, 누적 4, NF4/FP16로 유지한다. warmup은 전체 step의 약 5%, cosine 감쇠를 시작 제안으로 삼는다. 기존 B0와 warmup 규칙의 차이는 기록한다. 프로필 단독 B1은 기존과 같은 11 warmup step을 사용한다. 유효 배치와 실제 optimizer step·샘플 노출량·학습 토큰 수를 모두 기록한다.

1 epoch가 최적이라고 가정하지 않는다. 개발 실행 점수와 학습 곡선이 개선되면 동일 데이터에서 2 epoch 또는 LR 5e-5 중 하나를 별도 실험으로 검토한다. cosine이 끝난 기존 run에 step 수만 추가하는 방식은 쓰지 않는다. 장기 run은 처음부터 전체 스케줄을 고정하고, 중단 시 optimizer·scheduler·RNG·데이터 진행 상태까지 저장/재개한다.

## 7. 평가·선정·중단 기준

### 7.1 추론 조건과 환경

주 평가 환경은 기존과 같은 HF NF4 기반 모델+adapter, batch 1, greedy 한 후보, 최대 4,096 생성 토큰/600초를 기준으로 동결한다. `use_model_defaults=False`와 직접 전달한 `do_sample=False`를 확인하고, 요청 값뿐 아니라 실제 적용된 설정을 저장한다. 원문·종료 원인·토큰 수·경과 시간·샘플 ID를 남긴다. 실행 중단과 시간 초과도 전체 함수 분모에 포함한다.

B0와 후보를 같은 C 패널, compiler lock, 입력, 추론 backend로 평가한다. Ollama/F16 성능 확인은 별도 배포 검증이며, NF4 결과와 같은 열에 섞지 않는다. seed와 라이브러리 버전을 고정해도 GPU 간 바이트 단위 재현성까지 단정하지 않는다.

### 7.2 점수는 다음 세 층으로 구분

1. **원문 엄격 점수:** 모델 출력 자체에 복구 없이 verifier·지원 범위·컴파일·실행 검사. 경고도 실패.
2. **공통 프로필 적용 후 시스템 점수:** 사전에 고정한 CPU 속성 처리만 B0와 후보에 동일하게 적용. 명령/상수/피연산자는 변경하지 않음. 프로필 전후 검사·diff·해시를 남기며, 이를 원문 점수로 부르지 않음.
3. **로컬 편의 점수:** 정확한 `+sha` 무시 경고만 허용한 LocalTestPipeline 결과. 정식 원문 엄격 점수와 구분.

형식 적합률, LLVM 검증률, 컴파일률, 함수 단위 전체 입력 일치율, 카테고리·IID/OOD·난이도별 점수, 경고 종류, 완료율, 토큰 수와 지연시간을 함께 보고한다. 입력 평균 일치율이 함수 단위 실패를 가리지 않게 한다.

### 7.3 선정과 성공 목표

- B1 진입 전: 정답 프로필 변환·복원 전량 검증 통과, 원본 해시 보존, 명령/상수 불변 검사 통과.
- 개발 스크리닝 제안: 동일 50개 패널에서 B0보다 함수 성공 5개 이상 증가(+10%p), combined 10개 중 성공 2개 이상 증가를 유망 신호로 본다. 다른 분류에서 2개 이상 악화하면 원인을 조사한다. 표본이 작으므로 통계적 유의성으로 표현하지 않는다.
- checkpoint는 사전에 정한 적은 횟수의 개발 생성 평가로 선택한다. teacher-forced loss는 보조 진단으로 사용한다. 프로필 변경 전후 loss 절댓값은 직접 비교하지 않는다.
- 최종 시험은 **동결한 B0와 선택 후보 하나**를 같은 새 200함수에 평가한다. 전체/카테고리/IID/OOD 및 함수별 쌍대 승·패를 공개한다. 가능하면 family 단위 재표집 신뢰구간을 함께 보고한다.
- 방향성 목표는 **전체 75% 이상, combined 55% 이상**이다. 보장 성능이 아니며, 같은 시험에서 측정한 B0와의 차이도 함께 제시해야 한다. 역사적 65.5%와 단순 비교하지 않는다.
- 데이터/실행 검증 오류·분할 침범·출력 잘림을 발견하면 점수 계산 전에 수정한다. 생성 실패를 빼거나 시험을 보고 제한을 늘려 같은 점수를 대체하지 않는다.
- 개발 실행 점수가 두 평가 연속 개선되지 않거나, 회귀·비용이 커지면 추가 epoch/큰 모델 투입을 멈추고 반례와 데이터 분포부터 조사한다. 작은 표본의 한두 개 변동은 노이즈로 검토한다.

## 8. 자원 계획과 실행 순서

기존 측정값은 220 step 약 2.29시간, 시험 110함수의 T4 두 worker 작업 약 3.34시간이다. 아래는 그 값에서 단순 환산한 **계획용 경과 시간**이다. 새 출력 길이·평가 주기·GPU 가용성에 따라 달라진다.

| 단계 | 계획·상한 | 다음 단계 진입 조건 |
|---|---|---|
| 0. 로컬 준비 | 생성기/프로필/누출 검사 및 CPU 실행 검증 | 검사 통과; GPU 작업 없음 |
| 1. B0 기준 재측정 + B1 학습 | B1 학습 상한 3시간, 소규모 개발 추론 | 프로필 변경의 기능·길이 효과 확인 |
| 2. B2 학습 | 620/220×2.29 ≈ 6.45시간을 참고, 학습 상한 7시간 | 최대 길이 학습 step 메모리 시험 통과 |
| 3. 개발 패널 보완 | B0/B1/B2 소규모 추론 합계 상한 5시간 | 모든 후보에 필요한 패널을 같은 조건으로 완성 |
| 4. 새 시험 200개 × B0/후보 | 기존 속도로 약 12시간 + 준비 비용, 상한 14시간 | 후보/정책 동결 및 별도 자원 확보 |

**우선 개발 단계 상한은 합계 15시간, 최종 시험 자원은 별도 확보**한다. 이 수치는 단일/두 GPU 작업의 벽시계 합산 계획이며, 플랫폼 GPU 할당량·GPU 개수별 과금 단위와 동일하다고 가정하지 않는다. 실제 실행 전 현재 Kaggle 할당량과 세션 제한을 확인하고, 필요하면 주차/작업을 분리한다. Runpod 등 유료 자원은 당시 속도·메모리 시험 및 요금을 확인한 뒤 선택한다.

최종 200함수는 두 모델을 순차적인 독립 job으로 나누는 등 세션 한도를 피한다. 실패한 job 재개는 저장된 완료 ID를 재사용하며, 한 함수의 여러 후보 중 좋은 결과를 선택하지 않는다.

추론 전에 첫 5함수의 토큰/초와 메모리를 측정해 계획을 다시 계산한다. context와 출력 길이 변화가 있으므로 기존 11.285GiB 학습 peak만 보고 새 최대 길이도 들어간다고 가정하지 않는다. 반복적인 대규모 시험 추론보다 개발 패널을 먼저 사용한다.

- [LLVM add 명세](https://llvm.org/docs/LangRef.html#add-instruction): 상수 문자열보다 비트폭·오버플로 의미를 보존해야 하는 근거.
- [Alive2 공식 저장소](https://github.com/AliveToolkit/alive2): IR 간 refinement 검사 도구. 초기에는 반복 없는 10~20함수의 별도 연구로 검토한다. refinement 한 방향의 성공을 곧바로 양방향 동등성으로 해석하지 않는다. UB/poison, LLVM 버전, 지원 명령, timeout/unknown을 구분해야 한다. 반복문을 다룰 때 원본 C가 최대 16회라는 이유로 생성 IR도 그렇다고 가정하지 않는다.

**미확인:** 프로필 제거 후 토큰 감소율·실제 속도 개선, B1/B2의 실행 정확도, 새로운 최대 길이의 GPU 메모리, 새 family OOD 성능, 현재 GPU 할당량과 유료 자원 비용. 이들은 제안서의 효과 보장이 아니라 다음 실험에서 측정할 항목이다.
