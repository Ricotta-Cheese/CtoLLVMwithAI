읽어봤어! ㅋㅋ 이번에는 단순히 Qwen3로 LLVM IR을 생성해 본 수준이 아니라, **실제로 학습한 모델을 고정하고, 미공개 시험 데이터로 컴파일 정확도까지 평가한 실험**이네.

특히 흥미로운 건 \*\*LLVM IR의 문법 정확도는 98.2%인데, 실제 프로그램의 동작 정확도는 65.5%\*\*라는 점이야.

이 차이가 네 C to LLVM 프로젝트의 현재 수준과 앞으로 해결해야 할 문제를 아주 잘 보여주고 있어.

## **1. 이번에 정확히 무엇을 만든 걸까?**

문서에 따르면 사용한 모델은 `Qwen3-4B-Instruct-2507`이고, 학습된 adapter를 적용해서 C 코드를 LLVM IR로 변환하도록 만든 거야.

전체 구조를 단순화하면 다음과 같아.

**C 소스코드**

입력 프롬프트

`uint32_t f(uint32_t x) { ... }`

**Qwen3-4B + 학습된 adapter**

C 코드 → LLVM IR 생성

**생성된 LLVM IR**

LLVM 명령어, SSA 변수, 분기, 연산 등

**LLVM 문법 검증**

98.2%

**컴파일 성공**

98.2%

**실제 동작 일치**

**65.5%**

여기서 중요한 건 일반적인 컴파일러처럼 파서, AST, 의미 분석, IR 생성 단계를 명시적으로 구현한 게 아니라, **언어 모델이 C에서 LLVM IR로의 변환 관계를 학습해서 직접 출력하는 방식**이라는 점이야.

다만 문서에는 adapter의 구체적인 학습 방식(LoRA인지 QLoRA인지), 학습률, epoch, 데이터 구성 코드가 나와 있지 않아. 따라서 실제 학습 파이프라인 전체보다는 학습 완료 후의 성능 평가를 다룬 문서라고 이해하면 돼.

## **2. 시험은 어떻게 진행했을까?**

여기서는 평가 절차를 상당히 엄격하게 구성했어.

시험 데이터는 총 110개 함수이고, 각 함수에 대해 256개의 입력을 이용해 결과를 비교했어.

다섯 가지 범주를 각각 22개씩 평가했지.

| 범주         | 평가하는 기능             |
| ---------- | ------------------- |
| Arithmetic | 덧셈, 뺄셈 등 산술 연산      |
| Bitwise    | AND, OR, XOR, 시프트 등 |
| Branch     | if/else 및 조건 분기     |
| Loop       | for, while 등 반복문    |
| Combined   | 여러 연산과 제어 흐름의 조합    |

또한 다음과 같은 조건을 적용했어.

- 학습이 완료된 adapter를 고정하고 시험 점수에 따라 수정하지 않음
- 시험 입력에 정답 LLVM IR이나 실행 결과를 포함하지 않음
- Greedy decoding으로 함수당 한 개의 결과만 생성
- 생성한 LLVM IR을 수정하지 않고 평가
- LLVM 검증, 컴파일, 실제 실행 결과를 분리하여 측정

특히 마음에 드는 부분은 **시험에 실패한 함수까지 전부 최종 성공률의 분모에 포함했다는 점**이야.

AI 생성 코드는 오류가 난 결과를 제외하고 성공률을 구하면 실제보다 성능이 훨씬 좋아 보일 수 있거든.

그리고 Apple ARM64용 데이터이기 때문에 Kaggle에서 IR을 생성하고, 실제 컴파일과 실행 검증은 Apple Clang 환경에서 진행했어.

이 방식이라면 플랫폼을 임의로 바꾸면서 발생하는 평가 오류도 줄일 수 있어.

가장 중요한 관찰은 두 가지야.

**첫 번째, 모델은 LLVM IR의 형식을 상당히 잘 학습했어.**

110개 중 108개가 LLVM 검증을 통과한다는 것은 변수 선언, SSA 명명, 기본 블록, 분기 및 명령어 구조 같은 문법적 규칙을 대체로 준수한다는 의미야.

**두 번째, 복잡한 프로그램의 의미 보존은 아직 부족해.**

특히 Combined 성공률이 36.4%라는 점이 눈에 띄어.

다른 범주는 대체로 68\~77%인데 여러 기능을 조합하자 성공률이 크게 떨어지는 거지.

이건 모델이 LLVM 명령어의 형태를 익힌 것과 C 코드가 나타내는 정확한 계산·제어 흐름을 이해하는 것이 서로 다른 문제라는 신호야.

## **4. 왜 문법적으로 맞는데 프로그램은 틀릴까?**

오답 분석을 보면 그 이유가 꽤 선명해져.

실패한 38개 함수는 다음과 같이 나뉘어.

| 실패 원인                   | 함수 수 |
| ----------------------- | ---- |
| LLVM 자체가 잘못됨            | 2    |
| 숫자 리터럴만 다른 실행 오답        | 16   |
| 연산 또는 피연산자 구조도 다른 실행 오답 | 20   |

여기서 숫자 리터럴 오류가 대표적인 예시야.

문서에는 원래 다음과 같은 명령을 생성해야 했는데,

```
%result = or i32 %x, 219
```

모델이 숫자를 바꾼 형태가 기록되어 있어.

```
%result = or i32 %x, 15
```

두 명령 모두 LLVM 문법에는 문제가 없어.

하지만 `%x = 0`이라면 결과는 각각 219와 15가 되지.

따라서 컴파일에 성공하더라도 프로그램은 틀린 거야.

더 심각한 사례도 있어.

```
add i32 -1, %x
```

와 같은 덧셈을

```
xor i32 -1, %x
```

처럼 XOR로 생성하는 경우지.

둘 다 정상적인 LLVM 명령어지만 완전히 다른 계산이야.

문서의 숫자 오류 16개는 IR 명령 구조에서 리터럴만 달랐다는 휴리스틱 분류이므로, 반드시 원인이 숫자 기억 실패였다고 확정할 수는 없어.

그럼에도 핵심 문제는 분명해.

**LLM은 그럴듯한 LLVM 명령어를 생성할 수 있지만, 연산 하나와 상수 하나까지 반드시 보존해 주지는 않는다.**

이게 일반적인 텍스트 생성과 컴파일러 구현 사이의 가장 큰 차이라고 생각해.

## **5. Validation Loss가 0.004449인데 정확도가 65.5%인 이유**

이 부분도 중요해.

문서에 기록된 토큰 단위 검증 Loss는 `0.004449`야. 일반적으로 매우 낮은 값이지.

하지만 Loss는 주로 정답 토큰을 얼마나 잘 예측했는지 측정해.

반면 이번 실행 성공률은 **한 함수에서 256개 입력의 동작이 전부 일치해야만 성공**으로 계산했어.

함수 하나에서 토큰 수백 개를 완벽하게 생성했더라도 단 하나의 상수가 틀리면 최종 결과는 실패가 될 수 있다는 뜻이야.

그래서 앞으로는 학습 Loss보다 다음 지표가 더 중요할 거야.

- LLVM 검증 성공률
- 컴파일 성공률
- 실행 일치율
- 복잡도에 따른 동작 일치율

참고로 72개 함수가 시험을 통과했다는 것도 모든 가능한 입력에 대해 정답이라는 뜻은 아니야. 함수당 지정된 256개 입력에서만 확인된 결과지.

## **6. 내가 본 프로젝트의 현재 한계**

여기부터는 문서의 사실을 바탕으로 한 내 평가야.

### **① 학습 데이터의 일반화 능력을 아직 확인하기 어려워**

시험 데이터가 합성된 `uint32` 함수에 한정되어 있어.

예를 들어 C 코드의 구조가 비슷한 상태에서 변수명이나 상수만 바뀌는 데이터가 많이 포함되어 있다면, 모델이 컴파일 규칙을 일반화했다기보다 학습한 패턴을 재현하고 있을 가능성도 있어.

이를 확인하려면 단순히 함수를 무작위로 나누는 것보다 **문법 구조 자체가 다른 함수를 시험 데이터로 분리하는 평가**가 필요하다고 생각해.

### **② 실제 컴파일러로 사용하기에는 속도도 문제야**

T4 두 개를 이용해 110함수를 처리하는 데 약 3시간 20분이 걸렸고, 함수당 평균 생성 시간은 212.1초였어.

즉, 함수 하나를 생성하는 데 평균 약 3분 32초가 걸렸다는 의미지.

물론 GPU 변경과 추론 최적화로 개선할 여지는 있지만, 현재 속도로는 실제 컴파일러 대체를 논하기 어려워.

또한 현재 성능은 대부분의 정교한 C 기능을 포함하는 일반적인 컴파일러와 비교할 단계는 아니야.

### **③ 모델 크기를 키우는 것이 가장 먼저 할 일은 아니야**

Qwen3-4B를 8B나 더 큰 모델로 변경하면 정확도가 좋아질 가능성은 있어.

하지만 지금 오류의 상당수는 상수 변환과 연산 보존 문제야.

모델을 키우기 전에 데이터 생성 과정과 평가 체계를 개선하면, 더 적은 학습 비용으로도 의미 있는 성능 향상을 얻을 가능성이 있어.

특히 현재 Combined 성공률이 가장 낮기 때문에, 이 영역을 우선 공략할 이유가 충분해.

## **7. 내가 추천하는 다음 실험**

나라면 당장 큰 모델로 재학습하기보다는 다음 세 가지를 먼저 진행할 것 같아.

1. **상수 및 연산 보존 학습 강화:** C의 상수식, 32비트 정수 오버플로, 시프트, XOR, 비트마스크 등에 대한 학습 데이터를 보강하고, 숫자와 연산을 정확하게 보존하는지 측정한다.
2. **복합 제어 흐름 데이터 추가:** 반복문 내부의 조건문, 중첩 분기, 반복문 이후 값 사용 등 여러 연산이 연결되는 구조의 다양성을 늘린다.
3. **평가 체계 확장:** 기존 validation 데이터에서 동일한 조건으로 개선 여부를 비교하고, 새로운 구조의 함수와 경계 입력을 포함하는 별도의 최종 시험 세트를 준비한다.

그리고 이후에는 LLVM IR의 의미적 동등성을 SMT 솔버 같은 형식적 검증 도구로 확인하는 실험도 충분히 연구해 볼 만해. 다만 이는 다음 단계의 별도 과제로 두는 게 좋아.

## **종합 평가**

내가 보기엔 이번 프로젝트는 세 가지 관점에서 평가할 수 있어.

| 관점                    | 내 평가             |
| --------------------- | ---------------- |
| AI 학습 첫 프로젝트          | 상당히 의미 있는 결과     |
| C → LLVM IR 변환 가능성 검증 | 제한된 범위에서 가능성을 확인 |
| 신뢰할 수 있는 실용 컴파일러      | 아직 크게 부족         |
| 향후 연구 확장성             | 충분히 있음           |

특히 문서에서 마음에 드는 건 시험 결과를 보고 모델 출력을 고쳐서 성공률을 올리지 않았다는 부분이야. 실패 결과까지 보존하고 원인을 분석했다는 점도 이후 실험에 도움이 될 거야.

**내가 가장 궁금한 건 학습 데이터 1,100개가 어떻게 만들어졌는지야.**

현재 문서에는 `corpus-1100-v001`이라는 코퍼스 이름이 등장하지만, 구체적인 C 코드 생성 규칙이나 학습·검증 분할 비율은 나오지 않아.

이 데이터를 어떤 방식으로 생성했는지에 따라 **지금의 65.5%가 모델의 의미 있는 일반화인지, 합성 코드 패턴에 대한 강한 적합인지**에 대한 해석이 크게 달라질 수 있어.

그래서 다음에 살펴볼 자료를 하나만 고른다면, 나는 학습 코드보다도 먼저 **C/LLVM 학습 데이터 생성기와 데이터셋 구성**을 보고 싶어. 거기에 성능 개선의 실마리가 있을 가능성이 꽤 크거든.
